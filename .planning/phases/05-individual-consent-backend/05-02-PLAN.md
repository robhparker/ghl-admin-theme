## Phase Goal

Rob has everything needed to build and deploy the consent side in ClinX 365 and n8n: a step-by-step build spec for one consent Inbound Webhook workflow that resolves the exact contact by ID and either sends or refuses with a clear reason, a wf2 change so a member's own hub link shows only that member's card, and a member consent email in house style.

This plan writes the ClinX build spec (CONS-01..06). It runs in parallel with 05-01 (wf2) and shares no file with it. Names this plan fixes for the other plans: email template **"Member Consent Forms"**, subject **"Your Xcelsior consent forms"**, compiled from `Email-Templates/Consent-Hub-Invite/consent-forms-member.html` (Plan 05-03).

Planner findings this plan acts on:
- **F-2 (token length).** wf1 mints `crypto.randomBytes(16).toString('hex')` (32 hex chars) in Build Dependents and Prep Owner Update (Solo). D-05a asks for 32 bytes, and Rob's prefix note gives `adhoc_<64 hex>`. The spec uses 32 bytes (64 lowercase hex) after the `adhoc_` prefix, which matches D-05a's explicit size and keeps wf1's lowercase-hex alphabet. Plan 05-01's harness proves no consumer checks length. The spec records the wf1 fact.
- **F-3 (synthetic email).** wf1's Tag Dependent writes only `family-member` and `consent-pending`. The `synthetic-email` tag exists only on the 17 contacts the 2026-08-26 unified review tagged. wf1's synthetic address is `ownerlocal+<hint_patient_id>@ownerdomain`, and production ids look like `pat-EXAMPLEg7H8i`. So guard R-04 keeps D-04 #2 exactly (tag or empty email) and adds one OR condition with the same refusal message: email contains `+{{contact.hint_patient_id}}@`. This is labeled in the spec as a planner addition to D-04 #2. (Admin-theme's client pre-check `/\+\d+@/` misses `+pat-...@` addresses. That is a Phase 4 code note for Rob, out of this phase's scope, and recorded in the README by 05-03.)
